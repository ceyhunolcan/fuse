# Code Search current requirement

Implement `python -m fusecodesearch --request JSON`. Input has exactly `files` (list of `{path,language,source}`) and `pattern` string. Paths are distinct nonempty identifiers for supplied files; no filesystem access is required. Languages are `python` and `javascript`. Add JavaScript support and multi-token exact search to the starter's Python identifier search. Output is exactly `{matches:[{path,start,end,text},...]}` sorted lexicographically by path then increasing offsets. Offsets count Unicode code points, start inclusive/end exclusive; text is the original source slice. Include overlapping matches.

Token spelling determines exact matches; whitespace and comments are ignored for matching but retained inside reported spans. String literals are single tokens and their spelling is compared literally; identifiers inside comments/strings cannot match an identifier query. Python lexing handles indentation, multiline strings, operators and line continuations. JavaScript subset supports identifiers (including Unicode letters and `$`), numeric literals, single/double/backtick strings with escapes, line/block comments, punctuation and common operators. Template interpolation, regex literals and JSX are outside this subset. The source and pattern must be lexically valid in each supplied language; no complete AST validation is required. Empty file lists are valid; an empty/whitespace-only pattern is invalid. Unsupported languages, malformed files, duplicate paths and invalid tokens fail nonzero with no stdout and an error on stderr.

Implement only the documented current behavior.

### Lexical boundaries

This is a tokenization benchmark, not a complete Python/JavaScript parser. Python uses standard-library tokenization: ignore NEWLINE, NL, INDENT, DEDENT, COMMENT and ENDMARKER; reject tokenization errors and non-whitespace error tokens. Patterns may be fragments that tokenize successfully even if they are not valid complete programs, such as `a b`; unmatched delimiters that cause tokenization errors are invalid. Lexical name tokens, including keyword spellings, are identifier tokens for this benchmark. A comment-only pattern is invalid when tokenized for a supplied file. With no supplied files, only the nonempty/non-whitespace pattern-string check applies; no language is inferred.

The JavaScript dialect greedily tokenizes these forms, without AST validation: whitespace; `//` line comments; `/* ... */` block comments; single/double/backtick quoted strings, where a backslash escapes the next non-newline character; identifiers matching `(?:[$A-Za-z_]|[^\W\d])[$\w]*` under Python's Unicode regular-expression character classes; decimal digit sequences with an optional dot followed by digits; the operators `=== !== => == != <= >= && || ++ -- ...`; and single characters from `{ } ( ) [ ] . , ; : + * / % = ! < > ? & | ^ -`. Tokens are chosen in that order with longer listed operators before single characters. Any other character or an unclosed quote/comment is invalid. Numeric spelling is literal; exponent, radix and separator spellings have no special numeric-token meaning. Template interpolation, regex literals and JSX have no special syntax in this dialect. Quoted strings are opaque tokens; no escape decoding occurs for matching. As no AST is checked, a sequence of individually recognized tokens need not form a valid program. A `$name` identifier and a Python `...` token have ordinary literal meaning in A.
